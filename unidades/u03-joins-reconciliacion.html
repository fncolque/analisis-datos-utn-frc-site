Joins y reconciliación

Un join reúne tablas y, al hacerlo, puede conservar, descartar o multiplicar filas. Este capítulo enseña a anticipar ese efecto mediante la cardinalidad y a verificarlo después con conteos de filas, claves distintas y métricas reconciliadas.

Qué hace un join

Un join combina filas de dos relaciones a partir de una condición. La operación redefine la población de la consulta: determina qué registros aparecen, cuántas veces aparecen y qué columnas quedan disponibles.

La sintaxis expresa una decisión sobre el grano. Antes de ejecutar conviene declarar:

  1. tabla base;
  2. grano de cada tabla;
  3. clave de relación;
  4. cardinalidad esperada;
  5. cantidad esperada de filas;
  6. comportamiento de las claves sin coincidencia;
  7. métricas expuestas a repetición.

El resultado se controla después de cada relación. Este hábito permite localizar el paso que introduce una pérdida o una multiplicación.

Este patrón mide integridad:

SELECT COUNT(*) AS pedidos_sin_cliente
FROM pedidos_demo AS o

Claves y cardinalidad

Una clave primaria identifica una fila de su tabla. Una clave foránea referencia la clave de otra tabla. La cardinalidad describe cuántas filas pueden relacionarse a cada lado.

Relación Condición esperada Efecto al usar la tabla izquierda como base
Muchos a unoLa clave derecha es únicaConserva el grano izquierdo
Uno a muchosLa clave derecha aparece varias vecesLleva la salida al detalle derecho
Uno a unoAmbas claves son únicasConserva una fila por entidad
Muchos a muchosAmbas claves se repitenMultiplica combinaciones

La relación pedidos a clientes es muchos a uno. La relación pedidos a líneas es uno a muchos. La relación pedidos a productos se resuelve mediante la entidad intermedia sales_order_lines.

Verificar unicidad antes del join

El lado “uno” debe tener una clave única. La consulta siguiente busca clientes duplicados:

SELECT
    customer_id,
    COUNT(*) AS apariciones
FROM customers
GROUP BY customer_id
HAVING COUNT(*) > 1;

El release oficial devuelve cero filas. El mismo control se aplica a products.product_id, sales_orders.order_id y sales_order_lines.line_id.

Una clave repetida en customers haría que cada pedido de ese cliente aparezca varias veces. La condición SQL podría ser sintácticamente válida y producir totales inflados.

Primer join real: pedidos con clientes

SELECT
    o.order_number,
    o.order_date,
    o.channel,
    c.customer_name,
    c.segment,
    c.region
FROM sales_orders AS o
INNER JOIN customers AS c
    ON o.customer_id = c.customer_id
ORDER BY o.order_date, o.order_number
LIMIT 10;

La tabla base contiene una fila por pedido. customer_id es único en customers. La salida conserva una fila por pedido y agrega atributos del cliente.

El control utiliza LEFT JOIN:

SELECT
    COUNT(*) AS filas_despues_del_join,
    COUNT(DISTINCT o.order_id) AS pedidos,
    SUM(
        CASE
            WHEN c.customer_id IS NULL THEN 1
            ELSE 0
        END
    ) AS sin_cliente
FROM sales_orders AS o
LEFT JOIN customers AS c
    ON o.customer_id = c.customer_id;
filas_despues_del_join pedidos sin_cliente
357435740

La igualdad entre filas y pedidos confirma que el join conserva el grano esperado.

Reconstrucción progresiva del detalle

La consulta integrada parte de líneas porque la salida buscada conserva ese grano.

SELECT
    l.line_id,
    o.order_date,
    o.order_number,
    c.customer_name,
    c.segment,
    c.region,
    o.channel,
    p.product_name,
    p.family,
    l.quantity,
    l.unit_price_usd,
    l.discount_pct,
    p.standard_cost_usd,
    l.quantity
        * l.unit_price_usd
        * (1 - l.discount_pct) AS venta_neta,
    l.quantity * (
        l.unit_price_usd * (1 - l.discount_pct)
        - p.standard_cost_usd
    ) AS margen_bruto
FROM sales_order_lines AS l
INNER JOIN sales_orders AS o
    ON l.order_id = o.order_id
INNER JOIN customers AS c
    ON o.customer_id = c.customer_id
INNER JOIN products AS p
    ON l.product_id = p.product_id;

Cada relación agrega columnas y conserva una fila por line_id. Las métricas se calculan con cantidad, precio, descuento y costo estándar al mismo grano.

Reconciliación con la vista curada

Una reconciliación compara dos caminos que deberían producir el mismo resultado.

WITH reconstruido AS (
    SELECT
        l.line_id,
        l.quantity
            * l.unit_price_usd
            * (1 - l.discount_pct) AS venta_neta,
        l.quantity * (
            l.unit_price_usd * (1 - l.discount_pct)
            - p.standard_cost_usd
        ) AS margen_bruto
    FROM sales_order_lines AS l
    INNER JOIN products AS p
        ON l.product_id = p.product_id
),
totales AS (
    SELECT
        'tablas' AS origen,
        COUNT(*) AS lineas,
        ROUND(SUM(venta_neta), 2) AS ventas_netas_usd,
        ROUND(SUM(margen_bruto), 2) AS margen_bruto_usd
    FROM reconstruido

    UNION ALL

    SELECT
        'vista',
        COUNT(*),
        ROUND(SUM(venta_neta), 2),
        ROUND(SUM(margen_bruto), 2)
    FROM vw_ventas
)
SELECT *
FROM totales;

El riesgo de multiplicar una medida

Al unir pedidos con líneas, cada pedido se repite según su cantidad de líneas:

SELECT
    COUNT(*) AS filas_despues_del_join,
    COUNT(DISTINCT o.order_id) AS pedidos,
    COUNT(*) - COUNT(DISTINCT o.order_id)
        AS repeticiones_por_detalle
FROM sales_orders AS o
INNER JOIN sales_order_lines AS l
    ON o.order_id = l.order_id;
filas_despues_del_join pedidos repeticiones_por_detalle
750035743926

Los atributos de pedido se repiten 3.926 veces adicionales. Fecha, canal y cliente pueden repetirse porque funcionan como dimensiones de la línea. Un importe almacenado a nivel de cabecera quedaría duplicado al sumarlo en este resultado.

La protección depende del diseño:

  • agregar la medida antes de bajar al detalle;
  • seleccionar una fila de cabecera por pedido;
  • recalcular la medida desde componentes de línea;
  • conservar tablas de hechos separadas cuando existen procesos con granos diferentes.

DISTINCT aplicado al final puede esconder el síntoma y también eliminar observaciones legítimas. El control de cardinalidad ataca la causa.

Agregar después de unir

La consulta siguiente produce ventas por segmento desde las cuatro tablas:

    ROUND(SUM(

Consulta intermedia: los cinco clientes con mayor venta

SELECT
    c.customer_name,
    c.region,
    COUNT(DISTINCT o.order_id) AS pedidos,
    ROUND(SUM(
        l.quantity
        * l.unit_price_usd
        * (1 - l.discount_pct)
    ), 2) AS ventas_netas_usd,
    ROUND(
        SUM(l.quantity * (
            l.unit_price_usd * (1 - l.discount_pct)
            - p.standard_cost_usd
        ))
        / SUM(l.quantity
            * l.unit_price_usd
            * (1 - l.discount_pct)),
        4
    ) AS margen_pct
FROM sales_order_lines AS l
INNER JOIN sales_orders AS o
    ON l.order_id = o.order_id
INNER JOIN customers AS c
    ON o.customer_id = c.customer_id
INNER JOIN products AS p
    ON l.product_id = p.product_id
GROUP BY c.customer_name, c.region
ORDER BY ventas_netas_usd DESC
LIMIT 5;

CTE para separar etapas de control

Una consulta extensa gana trazabilidad cuando cada etapa recibe un nombre.

WITH lineas_con_producto AS (
    SELECT
        l.line_id,
        l.order_id,
        p.family,
        l.quantity,
        l.unit_price_usd,
        l.discount_pct,
        p.standard_cost_usd
    FROM sales_order_lines AS l
    LEFT JOIN products AS p
        ON l.product_id = p.product_id
),
detalle_comercial AS (
    SELECT
        lp.*,
        o.order_date,
        o.customer_id,
        c.segment,
        c.region
    FROM lineas_con_producto AS lp
    LEFT JOIN sales_orders AS o
        ON lp.order_id = o.order_id
    LEFT JOIN customers AS c
        ON o.customer_id = c.customer_id
)
SELECT
    COUNT(*) AS lineas,
    COUNT(DISTINCT line_id) AS lineas_distintas,
    SUM(CASE WHEN family IS NULL THEN 1 ELSE 0 END)
        AS lineas_sin_producto,
    SUM(CASE WHEN customer_id IS NULL THEN 1 ELSE 0 END)
        AS lineas_sin_cliente
FROM detalle_comercial;

Cada CTE puede ejecutarse de manera aislada durante el desarrollo. Los nombres describen la transformación y facilitan que otra persona revise el recorrido.

Otros tipos de join

Tipo Población conservada Uso habitual
INNER JOINCoincidencias de ambos ladosIntegración con relaciones validadas
LEFT JOINTodas las filas izquierdasEnriquecimiento y búsqueda de faltantes
RIGHT JOINTodas las filas derechasMisma lógica con la orientación invertida
FULL OUTER JOINAmbos ladosReconciliación de dos universos
CROSS JOINTodas las combinacionesEscenarios, calendarios o grillas controladas
SELF JOINUna tabla relacionada consigo mismaJerarquías o comparaciones internas

El recorrido práctico utiliza INNER y LEFT. FULL OUTER resulta útil para comparar dos sistemas de origen. CROSS JOIN exige estimar el tamaño: 1.000 filas por 500 filas producen 500.000 combinaciones.

Alias, ON y USING

Los alias acortan referencias y vuelven visible el origen de cada columna:

FROM sales_orders AS o
JOIN customers AS c
  ON o.customer_id = c.customer_id

USING (customer_id) ofrece una forma breve cuando ambos lados usan el mismo nombre. ON se prefiere en los primeros ejercicios porque deja escrita la relación completa y admite nombres diferentes.

Una condición por descripción, como nombre del cliente o producto, queda expuesta a cambios de escritura, espacios y homónimos. Las claves técnicas estabilizan la relación. Los campos descriptivos sirven como controles auxiliares.

Secuencia de depuración

Cuando un total cambia después de un join, la revisión sigue un orden concreto:

  1. ejecutar el resultado previo al join;
  2. contar filas y claves distintas en ambos lados;
  3. comprobar unicidad en el lado esperado;
  4. buscar claves sin coincidencia;
  5. ejecutar una sola relación;
  6. comparar filas antes y después;
  7. inspeccionar una clave que se multiplica;
  8. reconciliar una medida al grano correcto;
  9. agregar la siguiente relación.

Este procedimiento reduce el espacio de búsqueda. También produce evidencia útil para documentar la corrección.

Valores NULL después de una unión

Un LEFT JOIN introduce NULL en las columnas derechas cuando falta una coincidencia. El valor ausente debe conservarse durante el control. Reemplazarlo de inmediato con COALESCE puede ocultar la cantidad de casos incompletos.

Después de medir faltantes, una salida de consumo puede usar una etiqueta:

SELECT
    COALESCE(c.region, 'Sin región') AS region,
    COUNT(*) AS pedidos
FROM sales_orders AS o
LEFT JOIN customers AS c
    ON o.customer_id = c.customer_id
GROUP BY COALESCE(c.region, 'Sin región');

La etiqueta forma parte de la semántica publicada y debe quedar definida en el diccionario.

Auditoría de SQL asistido por IA

Una propuesta de join generada por IA debe declarar:

  • tabla base y grano inicial;
  • tabla incorporada y grano;
  • clave y cardinalidad;
  • tipo de join;
  • filas esperadas;
  • claves sin coincidencia esperadas;
  • medida que puede repetirse;
  • consulta de reconciliación.

La ejecución aporta conteos observados. La explicación humana compara esos resultados con la predicción y documenta cualquier ajuste.

Aplicación al caso

Cómo detectar si un join cambió el conjunto de datos

El release contiene 3.574 pedidos y 7.500 líneas. Unir pedidos con clientes conserva el grano de pedido cuando customer_id es único. Unir pedidos con líneas produce una fila por línea y repite los atributos de cabecera.

La suma segura utiliza medidas definidas al grano de línea. Los totales de cabecera requieren una agregación previa o una selección que evite repetirlos.
