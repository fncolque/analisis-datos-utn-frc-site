Lo que un modelo de IA sabe… y lo que no

Un modelo de lenguaje (LLM) genera respuestas a partir del contexto disponible. Para consultar datos de un sistema externo, la aplicación debe proporcionar herramientas y gestionar sus permisos.

Antes: una integración para cada par

Cada app de IA necesitaba un conector propio para cada sistema: 3 apps × 4 sistemas = 12 integraciones. Con MCP, cada sistema publica un servidor y cualquier app compatible se conecta: 3 + 4 = 7 implementaciones de interfaz. Las conexiones entre clientes y servidores siguen siendo independientes.

Las piezas: host, cliente y servidor

El host es la aplicación de IA (Claude, ChatGPT, un editor de código). Adentro está el modelo. Por cada servidor, el host abre un cliente MCP, una conexión separada. Cada servidor expone capacidades sobre un sistema.

Descubrir: ¿qué sabe hacer este servidor?

Al conectarse, el cliente pregunta qué ofrece el servidor. Los mensajes son JSON con el formato JSON-RPC. La respuesta describe cada herramienta: nombre, para qué sirve y qué datos necesita.

El catálogo entra al contexto del modelo

El host le pasa al modelo la pregunta junto con la descripción de las herramientas. Con ese texto, el modelo decide si conviene usar alguna y traduce “agosto” al argumento mes = "2026-08". Proponer no es ejecutar.

La persona aprueba

Antes de ejecutar, el host muestra qué herramienta se va a usar y con qué datos. La persona puede permitir o rechazar. Es el control humano, imprescindible si una herramienta pudiera modificar o borrar datos.

tools/call: el servidor ejecuta

El cliente envía la llamada. El servidor valida el argumento y ejecuta una consulta de solo lectura sobre el mart de ventas. Por dentro es SQL (o una API), como en el recorrido de API. Los valores son datos de ejemplo.

El resultado vuelve y el modelo responde

El servidor devuelve el resultado como contenido. El host lo agrega al contexto y el modelo redacta la respuesta en lenguaje natural, indicando qué herramienta y qué datos usó.

Registro, límites y riesgos

Cada llamada queda registrada: quién, qué herramienta, con qué argumentos, cuándo y qué devolvió. Se diseña con mínimo privilegio y con cuidado frente a instrucciones escondidas en contenido externo (prompt injection).

Resumen: API y MCP en el mismo pipeline

La API es el contrato que usa un programa. MCP es el enchufe común que usa una IA para descubrir y llamar herramientas, que por dentro pueden usar una API o una consulta SQL. La IA propone, el sistema controla, la persona decide.

Permisos y ejecución

La confirmación manual pertenece a este ejemplo. MCP no impone una interfaz de autorización: el host aplica su política. El acceso de solo lectura se debe imponer en los permisos del servidor y la base; una descripción de herramienta no lo garantiza. Los argumentos se validan y se usan como parámetros de consulta.
